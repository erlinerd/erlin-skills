# 目标

一个技能两种模式，按请求意图选：

- **制作模式**（写之前/写的时候）：引导式做课，核心纪律是逆向设计——**画像 → 目标 → 评估 → 骨架 → 正文**，评估先于内容。不允许拿到题目直接开写正文。
- **评审模式**（写完之后）：严格评审，只认条款和证据，每条问题三要素（位置、违反条款、修法），判决三档，不许"整体不错"式和稀泥。

用户请求同时含两种意图（"写完帮我审"）→ 先制作后评审，串行执行。

# 判断规则

- **模式判定**：出现"做/写/设计/备课/润色/改写"→ 制作；"评/审/验收/把关/自审/能上线吗"→ 评审。拿不准就问一句，不猜。
- **润色类请求不降级**：用户说"帮我润色/改写这段课件"时，仍先查目标与评估是否存在且对齐，缺就补齐并向用户说明，不只做文字活。
- **主题先行时先立目标**：用户只给主题不给目标，先产出目标草稿（Bloom 动词）给用户确认，确认后才进入评估设计。
- **项目标准优先**：项目有自己的课程标准（密度硬标准、词汇表约束等）时，以项目标准替换本技能对应默认值，其余流程照走；替换处在产出物里标明。
- **评审不改稿**：评审模式发现问题给出修法但不动手改；用户要改 → 切制作模式。
- **评审深度两档**：文档级（默认）——可访问性只核文档层可断定的项，UI 渲染层未核查项记 P2 并标「待产品级」；产品级（整条线上线验收或用户点名）——对交互组件做键盘走查与焦点对比度核查，两层都过才允许出产品级判决。
- **拿不准算不算问题**：记 P1 并写明不确定点，不静默放过。
- **与其他技能的配合**：

  | 技能 | 时机 | 职责 |
  | --- | --- | --- |
  | erlin-course（本技能） | 写之前/写的时候/写完之后 | 逆向设计制作 + 严格评审 |
  | erlin-dev-standards | 课件含交互代码时 | 代码实现的工程纪律 |
  | erlin-learning-plan | 个人系统学习 | 不做可教学课程，做学习计划 |

# 执行步骤 · 制作模式

1. **定画像与边界**（缺答案先问，不猜）：学员是谁、已会什么（先备）、时长预算、学完的边界（不学什么）、考核方式。用户只给了主题没给这些 → 先给出默认假设清单让用户确认，再往下走。
2. **写学习目标**：单课时 3–5 条，全部用 Bloom 可观察动词，句式「学完本课，学员能在<条件>下<行为动词><对象>，达到<标准>」。
   - 合格动词：列出、解释、举例、实现、演示、配置、对比、区分、定位原因、评判、辩护、设计、构建、重构、编写。
   - 禁用（必须行为化改写后才能用）：了解、熟悉、掌握、理解、知道、学会。
   - 改写示例——差：「了解 HTTP 缓存」；好：「给定一个缓存不生效的页面，学员能用 DevTools 定位缓存头问题，并在 10 分钟内修复」。
3. **先写评估，再写内容**：每条目标至少 1 条评估（测验题/动手任务/产出物），写完摆出三方对齐表（目标 × 评估 × 正文小节），出现空格就回去补齐。这一步不允许跳过。
4. **排课时骨架（Gagné 九事件）**：引起注意 → 告知目标 → 激活先备 → 呈现内容 → 学习指导（示例/脚手架）→ 引出练习 → 提供反馈 → 评估表现 → 保持与迁移。骨架先给用户过目，认可后再填正文。
5. **填正文（Mayer + 密度基线，默认值，项目明文标准优先）**：每站正文 ≥ 1500 汉字；交互组件不得连排，组件之间必须有正文过渡；交互后必带操作回顾 + 机制深析；大段有节奏切分、重点有信号标记、图示与说明相邻、对学员用第二人称。
6. **交付前过评审**：切评审模式自审（用户明确免审时可跳过），P0 清零才交付；P1 未清零时逐条列明留给用户决定。

# 执行步骤 · 评审模式

心里对照五套量表：逆向设计 UbD（目标↔评估↔内容三方对齐，一票否决区）、Bloom 修订版（动词可观察）、Gagné 九事件（骨架完整度）、Mayer 多媒体原则（图文与组件排布）、QM 8 大类 + OSCQR（兜底扫尾）。

1. **圈范围、拿材料**：确定评审对象是单站、单课（多站）还是整条课程线；拿到课件全文、学习目标声明（如有）、评估/测验题、学员画像。材料里没有学习目标声明 → 直接记一条 P0，不往下猜。
2. **对齐评审（一票否决区）**：动词审查（出现"了解/熟悉/掌握/理解/知道/学会"且无行为化改写 → P0）；三方对齐三查（每个目标 ≥1 条评估覆盖、每条评估回指某目标、正文支撑所有目标且超纲内容显式标注"选学/拓展"）；粒度（单课时目标 3–5 条，少于 2 或多于 6 → P1）。
3. **结构评审（Gagné 九事件，课时级对照）**：缺"告知目标"或"激活先备" → P1；缺练习或练习后无反馈 → P0（没有反馈的练习等于没练）；缺迁移设计 → P2。
4. **排版与多媒体评审（Mayer，逐条可查）**：连贯（删纯装饰）、信号（重点有视觉标记）、冗余（图文不逐句重复）、空间接近（图示与说明相邻）、分段（不整墙大段）、个性化（第二人称）。组件连排（两个以上交互组件中间无正文过渡）→ P1。
5. **评审表扫尾（QM 8 大类裁剪）**：课程概况、学习目标、评估与测量、教学材料、学习活动与互动、课程技术、学习者支持、可访问性。可访问性底线：文字对比度 ≥ 4.5:1、全流程键盘可达、图片有替代文本；核查深度按「评审深度两档」定。
6. **密度基线（默认值，项目明文标准优先）**：每站正文 ≥ 1500 汉字；交互后必带操作回顾 + 机制深析。不达标 → P1。
7. **整条课程线加查**：站间先备链无断链、难度坡度单调不陡跳、总时长在预算内。整线评审逐课全过，不允许抽样。

# 输出格式

- **制作模式交付序列固定**：画像假设清单 → 目标草稿 → 评估与对齐表 → Gagné 骨架 → 正文 → 自审报告（评审模式三档判决）。
- 目标与评估编号统一 `<G1>`…`<Gn>`、`<A1>`…`<An>`；对齐表按「目标 × 评估 × 正文小节」三列，摆不出无空格的表就没做完。
- **评审模式报告固定结构**：

  ```
  verdict: 过 | 有条件过 | 不过
  判决规则: 有任一 P0 → 不过；无 P0 且 P1 ≤ 2 → 过；其余 → 有条件过（修完 P0+P1 复审）

  P0（必须修，阻断上线）
  - <位置> 违反 <条款> 修法: <修法>
  P1（应修，修完复审）/ P2（建议）
  - 同上，三要素齐全
  ```

- 占位符统一 ASCII 尖括号；需要用户确认的槽位留空并明示等待确认。
- 评审表扬只允许指向具体条款（"目标-评估对齐完整"可以，"写得不错"不行）。

# 示例

## 用户问题

"帮我做一节讲 Git rebase 的课。" / "这个课时帮我过一遍，能上线吗？"

## 工具返回

前者：主题有了，画像/先备/时长未知 → 制作模式第 1 步先出假设清单。后者：拿到课件全文与评估题，无学习目标声明 → 评审模式先记 P0"缺学习目标声明"。

## 最终输出

制作：假设清单 + 目标草稿确认 → 评估与对齐表 → 骨架 → 正文 → 自审 P0 清零后交付。评审：三档判决 + 分级清单，每条问题 `<位置>` `<条款>` `<修法>` 三要素齐全。跳过前置步骤直接甩正文即违反本技能。

# 门禁

- **评估先于正文**：没有评估设计和对齐表，不允许开始写正文。
- **禁用动词必须改写**：目标里出现"了解/熟悉/掌握/理解/知道/学会"原样交付即不合格。
- **交付前评审 P0 清零**：制作模式没走评审自审（且用户未明确免审）就声称"做完了"即违反本技能。
- **三方对齐可检验**：目标、评估、正文小节必须能摆成一张无空格的对齐表。
- **没读到全文不给判决**：评审只看了大纲或片段时，输出只能是"材料不全"，不能是 verdict。
- **P0 定义不放宽**：目标缺失、不可验证动词、目标-评估不对齐、练习无反馈，四类永远 P0。
- **每条问题三要素**：缺一即评审不合格，打回重出。
- **判决只有三档**：过 / 有条件过 / 不过，禁止给分数或百分比制造精确感。
- **整线不抽样**：评整条线必须逐课过并逐一给结论。
