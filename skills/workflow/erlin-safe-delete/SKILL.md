# 目标

<goal>
让用户资产清理可确认、尽量可恢复：清单先行、批准后移入废纸篓，`rm` 直接删除是未经用户明示不得使用的最后手段。

背景（Why）：2026-09-07 误删 personos 项目目录（靠 git bundle 才救回）；2026-09-30 用户在清理会话中定规——删除前必须确认，同意后移废纸篓，不能直接删除。删除是不可逆操作，「快」没有「可恢复」值钱。

相邻分工：erlin-dev-standards 管 git/代码仓库内的破坏性操作门禁（reset --hard、force push 等）；本技能管整机文件系统层面的删除（目录、安装包、缓存、依赖）。删什么的策略判断（哪些该删）不在本技能范围，这里只管「怎么删才安全」。
</goal>

# 执行步骤

<workflow>
0. **区分范围与已有授权**：用户文件、项目目录、数据库、系统缓存清理走以下流程；对同一明确清单已有批准不重复确认。已授权代码删改（含任务必要的源码文件删除）可用版本控制保留差异；本次自建、已确认无用且不含用户数据的临时物可直接清理。来源不明、混有 WIP 或用户资产时按资产保护流程处理。
1. **清点**：对每个候选目标 `du -sh` 实测大小，产出编号清单；「建议删」与「建议留」分开陈述，用户数据和可再生缓存不合并成一个批准项，大小悬殊的项拆开（24G 固件目录不跟 184M 依赖目录并项）。
2. **确认**：清单呈给用户，请其按编号批准（如「1、2 可以删」）；**未获明确批准的编号项一个字节都不动**，不把「等」字里的目标解释成已批准。
3. **入废纸篓**：批准后逐条 `mv <路径> ~/.Trash/<原名>-<yyyymmdd-HHMMSS>`（同卷可快速移动并恢复；不会因此释放该卷空间）；需要 Finder「放回原处」语义时改用 `osascript -e 'tell application "Finder" to delete POSIX file "<路径>"'`。
4. **不可入废纸篓的删除**（`brew cleanup`、`npm cache clean`、`pnpm store prune`、`xcrun simctl erase` 等自清理命令）：同样先确认，注明「此项无法入废纸篓」，获准后执行。
5. **报告**：逐条说明移入废纸篓或实际删除结果；腾空间任务测量 `df -h` 前后变化。同卷入废纸篓不释放空间，清空废纸篓需另获明确授权；不能把移动大小当成释放容量。失败不静默降级为 rm。
</workflow>

# 判断规则

<rules>
- 「删除」覆盖面：rm/unlink/rm -rf、覆盖式 mv、以及一切内部会删数据的命令（包管理器缓存清理、设备/模拟器擦除、应用更新器缓存）。
- 批准粒度 = 清单编号项；「全删」覆盖呈报清单的全部编号项，未呈报的目标不在授权范围内。
- 有重建成本的项单独标注成本（node_modules 删后要 `pnpm i`；DerivedData 删后首次构建变慢），让批准是知情的。
- 活跃资产默认建议保留：正在开发的项目依赖、用户明示保留的目录（如微信）。
- `~/.Trash` 清空本身也是删除动作，同样走本流程确认。
- 与其他技能的配合：

| 技能 | 时机 | 职责 |
| --- | --- | --- |
| `erlin-dev-standards` | 仓库/git 层 | 破坏性 git 操作的授权与回滚方案 |
| 本技能 | 用户资产/系统清理 | 既有授权检查、确认与废纸篓落地 |

</rules>

# 输出格式

<output-format>
输出载体：下面两个模板的 ``` 围栏只是展示格式；实际输出直接写渲染态 markdown——条目用表格、汇总用列表，整份清单/报告不得包进代码块，用户端必须看到渲染后的表格而非等宽原文。条目仅 1–2 项时可用编号列表代替表格。

确认清单模板（编号项是批准与报告的锚点）：

```
待删清单（回复编号批准，如「1、3」）：
| # | 路径 | 实测大小 | 建议 | 一句理由/重建成本 |
| --- | --- | --- | --- | --- |
| 1 | ~/Downloads/i4ToolsDownloads | 24G | 删 | 固件包可重新下载 |
| 2 | ~/code/projects/x/node_modules | 184M | 留 | 活跃项目，删后需 pnpm i |
```

完成报告模板（编号与批准清单一一对应，逐行可核对；「去向」写实际动作，不写概括语）：

```
删除结果：
| # | 路径 | 大小 | 去向 | 状态 |
| --- | --- | --- | --- | --- |
| 1 | ~/Downloads/i4ToolsDownloads | 24G | ~/.Trash/i4ToolsDownloads-20261001-141020 | 已入废纸篓（可恢复） |
| 2 | brew cleanup | — | 已执行 brew cleanup | 已删除（不可恢复，经批准） |
| 3 | ~/Library/Developer/CoreSimulator | 14G | — | 未动（未获批准） |

汇总：
- 可恢复：24G 在废纸篓（Finder 右键「放回原处」恢复；清空后不可恢复）
- 实际释放：0B（同卷移入废纸篓不释放空间；清空废纸篓后约回收 24G，需另行确认）
- 磁盘实测：<df 前值> → <df 后值>（差值 <Δ>）
```

（示例算术：可恢复/预计回收只合计已入废纸篓的编号项——上例仅第 1 项 24G；「已删除（不可恢复）」项不计入可恢复，未动项不计入任何合计。）

报告规则：

- 每个编号项必须单独一行，不得合并成「已入废纸篓：A、B、C」式罗列。
- 「实际释放」只写 df 实测差值；入废纸篓的大小归入「可恢复」，两者不得混报。
- 失败项如实标「失败：原因」，不得省略。
- 禁止把清单或报告包进 ``` 代码块输出。
</output-format>

# 门禁

<gates>
- 用户资产未确认不删：具体清单未批准就等待，不顺手扩展目标；明确已有授权、代码删改与自建临时物按步骤 0 判断。
- 禁止对用户资产清理目标使用 rm/rm -rf，除非用户消息明确说出「直接删」「不用废纸篓」类指令；即便如此也先复述目标再执行。
- `mv` 入废纸篓失败（跨卷、权限、~/.Trash 异常）必须停下报告，不得静默改用 rm。
- 工具自清理命令（不可入废纸篓类）未经批准不得执行。
- 资产清理逐条报告，腾空间任务附实测 df；同卷移动不能报告为释放空间。
</gates>
