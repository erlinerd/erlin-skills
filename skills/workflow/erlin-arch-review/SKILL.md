erlin-arch-review — 架构与设计原则审查

# 目标

对仓库/模块/组件/一次 diff 从七个设计原则做证据驱动的评估。输出：七张原则评估卡 + 一张整改清单。原则：**每个判断必须带证据（文件 + 行号 + 具体代码形态）**；证据不足的项标"未评估"；评分 1-5。也适用于 erlin-autopilot 跑完后想要架构视角的审查。

# 执行步骤

1. **定范围**：仓库 / 模块 / 组件 / 这次 diff——用户没说明时默认"关键路径 + 最近一次 diff"。范围小到一轮能看完，大了先圈定子模块。
2. **相关设计与验证证据**：检查公共契约、复用与行为覆盖是否足以支撑当前改动；缺失作为发现记录，不要求先整改才能继续架构评审。内部辅助函数不要求签名审批，测试按行为和风险判断，不逐签名计数。只有任务确实采用 BDD 时检查其场景约定。
3. **按规模选择审查方式**：小型或聚焦问题可在主会话直接审；跨模块、大型 diff 或需要独立视角时再用子代理。工具不可用时可直接完成并说明局限；没有“每次必须不同上下文”的门槛。使用子代理时划清范围，主会话复核高影响结论和证据后转达。
4. **逐原则评估**：按判断规则里的七原则判据/信号/证据逐个出独立评估卡（按 1→7 顺序跑）：每原则 1-5 分 + 一句理由；最关键问题 1-3 个，按"证据 → 影响 → 建议改法"三段写。**解耦与模块化是重点维度**（原则 1/3/4 联合深挖）：跨层依赖方向、domain 逻辑住址、模块边界清晰度、hub 文件——这四项任何一个失分都要单独成卡详述。
5. **排整改清单**：跨原则合并去重，按 **影响 × 成本** 排序，标注原则来源；前三项标"优先做"。**每项必须给修复建议三要素**：具体改法（改哪个文件/怎么改）、验收标准（怎么算修好，最好落到测试）、成本估算。
6. **出报告**：总览表 + 七张原则卡 + 整改清单（模板见输出格式）。**详细全面、零废话**：每张卡的证据链完整（这是"详细"），但禁止客套、禁止与总览重复的展开、禁止"总体而言"式总结段。决策就绪，不贴原始代码 dump（需要引用时给文件:行号）。

# 判断规则

七原则（每个独立评估卡；按此顺序跑）：

### 1. 单一职责 SRP

- **判据**：一个模块/类/函数只有一个改变理由。
- **信号**：类名是多连词（`UserManagerAndExporter`）、一个函数同时干校验+IO+格式化、超过一两屏的职责列表。
- **证据**：点名具体类/函数，数它内部在服务几个不同的"为什么要改"。

### 2. 开闭原则 OCP

- **判据**：真实、反复出现的扩展是否导致多处易错修改；权衡扩展收益与抽象成本。
- **信号**：同一变化需要同步多处决策逻辑并已有遗漏或分歧。有限、封闭集合的集中 `switch` 往往更清晰，缺少策略/工厂本身不是缺陷。
- **证据**：结合近期变化与预计扩展点说明具体维护风险；不以“修改了既有代码”或改动处数大于零机械扣分。

### 3. 低耦合

- **判据**：模块间依赖少、明确、单向。
- **信号**：import 满天飞、A 深入 new B 的内部对象、一个模块改动牵动全网、缺少清晰接口（深模块：小接口、少依赖、多行为）。
- **证据**：画出模块 import/调用图，标出 hub 节点（被几十处依赖的）和环。

### 4. 简洁架构

- **判据**：分层清晰（domain → application → infrastructure → presentation），依赖永远指向内层。
- **信号**：业务规则散在 UI/网络/数据库层、循环依赖、数据库框架的类型泄漏进 domain、改数据库要连带改业务代码。
- **证据**：指出业务逻辑实际住的地方，和它该住的地方的差距。

### 5. UI/服务分离

- **判据**：UI 层不掺业务逻辑与数据访问；服务层不掺展示。
- **信号**：ViewController/组件/页面里直接查库、拼 API、算业务规则；服务返回格式化好的展示字符串。
- **证据**：引用具体组件里的越界代码行。

### 6. 设计模式运用

- **判据**：模式用在解决真实结构问题上，不是炫技；重复出现的结构该有模式的形态。
- **信号**：模式滥用（到处 Singleton/观察者）、该抽象处复制粘贴、模式名字当变量名用（类名叫 `XXXObserver` 却没观察者语义）。
- **证据**：一处滥用一处缺失各举一例。

### 7. 组件复用

- **判据**：可复用单元被真正抽出并被多处使用；公共代码不复制。
- **信号**：跨页面/模块重复的组件与代码块、复制三次以上的函数、复用组件参数化程度不足（只能复制改）。
- **证据**：点名重复组和它的出现次数（精确 grep 计数）。

**与 diff 合规评审的分工**：diff 级合规评审（standards + spec 两轴：对没遵守约定、没实现需求）由模型按 erlin-dev-standards 直接执行；本技能是架构级、看"设计得怎么样"（值不值得长期住在里面）。是否组合取决于用户要求与审查范围，不强制重复评审。

| 评审 | 回答的问题 |
| --- | --- |
| diff 合规自查（按 erlin-dev-standards） | 这次改动守约了吗？实现规格了吗？ |
| `erlin-arch-review` | 代码结构值得长住吗？ |
| `erlin-product-review` | 产品值得做吗？做得好吗？怎么更好？ |
| `erlin-autopilot` | 一堆任务怎么并行又快又稳地做完？ |

erlin-autopilot 的门禁默认做 diff 两轴自查；想要架构视角就再跑一次 `erlin-arch-review` 技能——它不限于 diff，能评整个代码库，正好补 erlin-autopilot 只看合并结果的盲区。

# 输出格式

报告 = 总览表 + 七张原则卡 + 整改清单 + 未评估，模板：

```markdown
## 总览
| 原则 | 分(1-5) | 一句话 |
|---|---|---|
| 单一职责 | 3 | UserManager 干三件事 |
| 开闭原则 | 2 | 加类型要动 4 处 switch |
| … | | |

## 单一职责
最强项：…
关键问题：
1. [证据: file.py:120] → [影响] → [建议]

## 整改清单（影响×成本排序，前三项优先做）
1. (耦合) 抽 API 层接口，斩断 UI→DB 直连 → 2 天
2. …

## 未评估
（证据不足的项，标注需要什么证据：测试、调用链、或哪个模块）
```

# 示例

## 用户问题

"帮我用架构视角 review 这次 diff，重构建议给一份，重点看看耦合。"

## 工具返回

### 子代理（并行分片审查报告）

耦合分片：`services/StudySessionService.swift:88` 直接 new 数据库仓库对象，且被多个 View import（hub 节点）；复用分片：某卡片组件跨 3 个页面复制粘贴（grep 计数 3）；"有测试兜底"论断待复核。

### grep（主会话交叉验证抽查）

`grep -rn` 复核 hub 论断成立；复核"有测试兜底"为不存在 → 该论断剔除，不入报告。

## 最终输出

- 总览表：七原则各 1-5 分 + 一句话（如：单一职责 3「UserManager 干三件事」、开闭原则 2「加类型要动 4 处 switch」）。
- 整改清单（影响×成本排序，前三项优先做）：如「(耦合) 抽 API 层接口，斩断 UI→DB 直连 → 2 天」，每项带具体改法/验收标准/成本估算。
- 未评估清单：证据不足项标注需要什么证据（测试、调用链、或哪个模块）。

# 门禁

- 每个判断必须带证据（文件 + 行号 + 具体代码形态）；证据不足的项标"未评估"，不许脑补评分。
- 设计或测试证据不足列为发现或未评估，不阻塞其他架构维度评审。
- 子代理按规模与独立审查价值选用，主会话可直接审查；转达子代理发现前复核高影响证据。
- 报告零废话：禁止客套、禁止与总览重复的展开、禁止"总体而言"式总结段；不贴原始代码 dump（需要引用时给文件:行号）。
- 整改清单每项必须含三要素：具体改法（改哪个文件/怎么改）、验收标准（怎么算修好，最好落到测试）、成本估算；前三项标"优先做"。
