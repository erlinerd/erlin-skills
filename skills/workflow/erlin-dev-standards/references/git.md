# Git 工作流与提交规范

本索引承载 `erlin-dev-standards` 中的 Git 相关规则：Worktree、仓库分支策略和提交信息。worktree 规则（§1）是唯一权威源——编排技能（erlin-autopilot）原生回退时引用本节，不另立副本。

## 1. Worktree 规则

需要隔离改动或并行任务时用 `git worktree`。**默认建在仓库外、与仓库平级**，不默认放仓库内 `.worktree/`：

```
workspace/
├── repo/
└── repo-worktree/
    ├── account-deletion/      ← task slug
    └── fix-login-crash/
```

- 目录名用 task slug（小写 kebab-case），不复制分支名中的 `/`：分支 `feature/123-account-deletion` → 目录 `../<repo>-worktree/account-deletion`。
- 例外：环境（沙箱/权限）不允许写兄弟目录时，先向用户说明，征得同意后回退仓库内 `.worktree/`，并确保该路径已进 `.gitignore`。
- 既有不合本约定的 worktree 先问再动，不擅自迁移、改名或删除。

### 1.1 创建前检查（缺一不做）

不无条件 `git worktree add`。创建前逐项确认：

1. 仓库根（`git rev-parse --show-toplevel`）；
2. 主工作区状态（`git status`；未提交改动不会带入 worktree）；
3. 目标分支是否已存在——**已存在则恢复**（在其上开 worktree 或进入已有 worktree），不重建重复分支；
4. base branch 是否正确（按 §2）；
5. 已有 worktree（`git worktree list`），沿用现有布局与命名；
6. 目标路径无冲突。

```bash
# 新任务（分支不存在）：
git worktree add ../<repo>-worktree/<slug> -b <task-branch> <base-branch>
# 恢复（分支已存在）：
git worktree add ../<repo>-worktree/<slug> <existing-branch>
```

### 1.2 使用与清理纪律

- 一个独立任务一个分支、一个 worktree；并行 agent 禁止操作同一个 working tree。
- 基于**已提交的基准**创建；跨任务依赖用依赖边表达，后继 worktree 可从依赖任务的分支开出。
- 创建后用项目既有 setup 方式初始化（装依赖；XcodeGen/Tuist 等生成型工程先生成再构建）。不复制 secrets。
- worktree 不是安全沙箱：在 worktree 里干活不放宽《安全与失败处理规范》的任何授权边界。
- **不默认删除**。清理前全部确认：无未提交的有用工作；提交可从保留分支到达；任务已合并 / 已放弃 / 已归档三者其一；没有活跃 agent 正在使用。

```bash
git worktree remove ../<repo>-worktree/<slug>
git worktree list   # 确认已清空
```

## 2. 分支与基准

优先遵循仓库现有策略和用户授权，不全局强制 Gitflow。没有明确策略时选择任务的正确基准与描述性分支（如 `fix/login-crash`）；不为流程创建 `develop`，不虚构 issue id，不重命名历史分支。只有仓库本来使用 Gitflow 时才沿用其 develop/main/release 关系。合并目标和是否合并取决于交付点，待审分支也是有效交付。

## 3. 提交规范

### 3.1 语言偏好

提交信息优先使用用户、本项目或仓库约定的本土语言。当前默认偏好为**中文**；如果仓库已有明确的英文提交规范、自动化校验或团队要求，则遵循仓库约定。

代码符号、分支名、版本号和必要的标准术语保持原文，不为翻译而翻译。

### 3.2 提交粒度

- 仅在用户授权 commit 时提交；已有授权无需重复确认。按单一意图组织提交，并完成与改动风险相称的验证（见《验证与排障规范》）。
- 一个提交表达一个完整、可独立理解的意图。
- 不把无关格式化、临时调试、别的功能或他人的 WIP 混入提交。
- 提交前检查 `git diff`、`git diff --cached` 和 `git status`，确认暂存范围属于当前任务。
- 有冲突时先解决并验证，再提交；不提交冲突标记。

### 3.3 提交标题格式

默认使用简洁的 Conventional Commits 结构，类型保留英文，描述使用中文：

```text
<type>: <中文描述>
```

可用类型：

- `feat`：新增功能
- `fix`：修复问题
- `refactor`：重构，不改变外部行为
- `perf`：性能改进
- `test`：测试变更
- `docs`：文档变更
- `build`：构建或依赖变更
- `chore`：维护性变更
- `style`：不影响逻辑的格式或样式变更
- `revert`：回滚提交

需要范围时可写：

```text
feat(artist): 重设计歌手详情页
```

标题使用祈使、明确、短句，建议不超过 72 个字符；避免 `update`、`fix stuff`、`修改一下` 等无法说明结果的标题。

### 3.4 提交正文

改动较大或原因不明显时添加正文，说明：

1. 改了什么；
2. 为什么改；
3. 如何验证。

正文可使用中文短段落或列表。不要写入 secret、token、私钥、个人信息或生产连接串。

```text
feat(artist): 重设计歌手详情页

- 将歌曲与专辑拆成分区和子页
- 保留资料库歌曲并增加横向专辑 shelf
- 已验证 iOS 模拟器与 macOS 构建通过
```

### 3.5 合并与发布提交

- 合并提交应明确说明来源和目的，例如 `merge: 合并歌手详情页改版`。
- 发布提交使用 `release: 发布 1.1.0`；紧急修复使用 `hotfix: 修复播放崩溃`，除非仓库要求保留标准类型。
- `commit`、`push`、创建 PR、改写共享历史各按现有授权执行；实现授权本身不等于这些动作的授权。

## 4. 并行优先（多任务调度）

多个可独立推进的任务并存时（多张票、多个 feature、多个待修问题），**默认先评估并行**，不默认顺着列表逐个做。选择串行必须说明理由：文件重叠、阻塞边或成本，三者之一即可；没有理由的串行是偷懒，没有判据的并行是赌博。

### 4.1 可并行判据（两条同时满足才并行）

1. **文件/缝不重叠**：各任务的改动文件集合不相交。触碰同一文件、同一模块缝（route 接线、共享类型、生成配置、公共组件）的任务排串行。
2. **无阻塞边**：一个任务的产出不是另一个任务的输入。有依赖的按依赖图排序（拆票时的 blocking edges 直接当分组判据用）。

判据不满足但任务又急时，先做**切缝**评估：能否抽公共接口/类型让两边独立？不能就老实串行，不为并行制造虚假隔离。

### 4.2 执行载体：一任务一 worktree

- 每个并行任务一个 worktree + 独立分支（命名遵循 §2，落点与生命周期遵循 §1），互不污染工作区。
- **已有编排器被有意启用时**（如 pi-git-worktrees 等环境编排器）：由编排器拥有 worktree 生命周期——先读其当前安装版本的编排指引再执行，不硬编码 CLI 参数；本技能的 §1 规则仍约束分支命名、并行判据与授权边界。
- **无编排器时**：ZCode 环境用子代理（Agent 工具）或后台任务并行执行，worktree 按 §1 开；一任务一 worktree。
- 生成型工程（XcodeGen/Tuist）的并行单元各自先生成工程再构建；数据库/端口类资源冲突在派活前分配好。

### 4.3 上限与合并纪律

- 同时活跃 ≤3 个并行单元；LLM 通道有速率限制（如 GLM 持续 429）或 token 成本敏感时取下限（2）。
- 合并**逐张收、逐张过验证门**：merge 一张 → 全量门禁全绿 → 再收下一张；不攒批合，不并行合。
- 在合并已获授权时，合入 base branch 遵循 §2 的仓库策略，不默认写死 `main`。
- 出现合并冲突即停：把后续同区域任务改为串行，冲突不在并行状态下硬解。
- 并行不豁免验证：每个单元内部契约先行、测试、门禁照常；「并行」从来不是「省检查」的理由。
