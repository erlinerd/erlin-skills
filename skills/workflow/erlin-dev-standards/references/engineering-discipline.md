# 工程改动纪律

本索引承载 `erlin-dev-standards` 的改动设计与协作纪律。

## 1. 落笔前先读

添加或修改代码前，读三样东西：目标文件的导出接口、它的直接调用方、同层已有的公共工具函数。不理解既有设计为何这样设计时，先问，别改；既有设计往往编码了看不到的约束。

怎么读：查调用方、数据流或模块边界时，**优先用 codegraph 类语义索引工具**（仓库已 `codegraph init` 时，按符号名/调用路径直接问，比按文件名 grep 更不容易漏掉间接引用）；索引不存在或查不到时退回 grep + 通读。工具是加速器不是替代——索引给的是定位，约束与意图仍要读源码确认。

## 2. 最小切口

只改绝对必要的部分，不顺手优化相邻代码、注释或格式。只清理自己引入的东西；发现旧问题就记录为独立事项。动手前检查 formatter/linter 配置、同目录 2–3 个邻近文件、最近 5 个提交的粒度与信息格式；一致性优先于个人品味。

## 3. 简单至上

用最少代码解决当前问题，不写猜测性实现，不实现需求之外的功能。抽象等到第三次重复；测试代码不受此限制。以下任一信号出现时停下重想：单函数超过 60 行、嵌套超过 3 层、新增参数超过 5 个、为一处调用新增一层抽象、单个 PR 新增文件数超过删除+修改文件数。

## 4. 冲突显式暴露

发现两处模式互相矛盾时，明确择一，说明选择理由，把另一处标为待清理。不要把两种冲突范式强行融合。

## 5. 检查点

改完一个文件、跑完一次验证，或连续 5 次工具调用未验证时，报告：做完了什么、验证到什么程度、还剩什么。上下文丢失或方向不确定时重述状态，不凭残缺记忆继续。

## 6. 契约先行与复用盘点

公共接口、跨模块协作和实现票据需要明确契约，内部辅助函数不逐个审批签名。沿用已有需求、规格和用户授权；只有无法从上下文确定的产品、兼容性或权限决策才需要确认。

### 6.1 复用盘点

先查项目内相关组件、公共工具与依赖能力；陌生 API、版本兼容或方案选择再查官方资料。记录足以支持决定的路径或来源，不要求每次局部修改都做社区调研。

### 6.2 契约清单

对外承诺包括出入参、错误、边界、并发隔离与兼容性；需要对接时用类型与签名表达。无需先造空实现或新增审批阶段。任务级交付与验收见 [Spec 契约标准](spec-contract.md)，不重复定义。

### 6.3 验证清单

按可观察行为和风险选验证。新增行为、修复缺陷或覆盖不足时补必要测试；能复现的 bug 优先用回归测试证明修复。文案、低风险配置和已有充分覆盖的改动可用现有检查；无法自动化时报告人工验证和限制。用户要求 TDD/BDD 时遵循对应流程，不把每个内部签名都映射成一条测试。
