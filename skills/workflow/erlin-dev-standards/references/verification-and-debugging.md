# 验证与排障规范

本索引承载 `erlin-dev-standards` 的证据闭环、验证门和排障规则。

## 1. 证据闭环

只有真正跑过且退出码为 0 的命令才能说“已验证”或“已通过”。没跑过的标为建议或待运行；跳过步骤必须明确说明；报告失败时保留原文报错行和退出码。

## 2. 最窄验证门

按改动风险选最便宜的可复现验证，不无脑跑全量流水线。验证顺序从**局部、便宜**到**全局、昂贵**：

```
定向测试 → 相关套件 → 静态/类型检查 → lint → build → 集成 → E2E
```

按改动风险在这条链上截断：日常小改或重构，涉改模块构建成功 + 定向测试通过即可；只有不可逆操作、跨模块影响或回滚成本高的改动，才升级到集成测试与全量构建。只运行项目真实存在且与改动相关的检查；禁止声称未实际运行的检查「通过」；跑不了的检查明确说明原因。

保留已经启动的服务、模拟器和调试 session，不随意重启或重置。

## 3. 假设—溯因排障

遇到 bug 或报错，不猜着改：

1. 列出 1–3 个最可能原因，按概率 × 验证成本排序；
2. 构造最小可复现用例，逐一验证假设；
3. 证实后做最小切口修复，并补防回归测试。

连续三次修复失败就停止，明确最可疑的假设；不要在错误前提上继续加码。

## 4. 测试验证意图

断言业务后果，而不是只断言函数被调用、返回非空或字段存在。每个用例独立初始化依赖，不依赖共享单例状态或执行顺序。

## 5. 按风险选择验证

- 行为变化、缺陷修复和高风险边界需要有能发现回归的验证；现有覆盖不足时补测试，不要求每改一个文件就新增测试。
- 文案、低风险配置、机械修改或已有充分覆盖的改动，优先运行现有相关检查，不新增只重复实现的测试。
- 正确实现新行为、保持外部行为的重构后，测试仍绿是正常的；破坏约定行为却未失败才提示断言或覆盖缺口。
- 完成报告注明实际命令、结果及限制。选定的相关检查应通过；失败、未运行或环境受阻如实说明，不宣称全绿，也不因无关历史失败扩展任务。
- commit 需要用户授权；验证范围遵循上述风险判据，不把未跑全仓测试当作一律禁止交付的理由。
