# 目标

写代码时的通用工程规范（任何语言任何项目）——改动前先读、最小切口、证据闭环、失败不静默。本技能是执行摘要：主文件负责回答“必须做什么”，`references/` 主题文档负责回答“怎么做、为什么、有哪些例外”，也是唯一 Policy Source。

主题索引：

- [工程改动纪律](references/engineering-discipline.md)：先读、最小切口、简单至上、冲突处理、检查点。
- [Spec 契约标准](references/spec-contract.md)：任务级 Spec 的触发线、必备字段、验收线与模糊描述禁令。
- [验证与排障规范](references/verification-and-debugging.md)：证据闭环、按风险验证、假设—溯因与测试意图。
- [安全与失败处理规范](references/safety-and-failure.md)：错误处理、敏感数据、破坏性操作。
- [Git 工作流与提交规范](references/git.md)：Worktree、仓库分支策略、提交授权与提交信息。

# 执行步骤

1. **先读再写**：改代码前阅读目标文件的导出接口、直接调用方和同层公共工具；理解调用关系与架构时优先用 codegraph 类语义索引工具（按符号查，不按文件名猜）；同时检查格式化/工程约定与最近提交粒度。不理解既有设计时先停下，不凭猜测修改。
2. **最小切口**：只改需求必要部分；不顺手重构、格式化或修复无关旧问题。抽象等到第三次重复；单函数超过 60 行、嵌套超过 3 层、新增参数超过 5 个等信号出现时停下重想。
3. **按边界明确契约**：公共接口、跨模块协作和实现票据先明确出入参、错误、边界、并发隔离与验收，必要时写类型和签名。先检查项目内已有能力，遇到陌生 API 或选型问题再查官方资料。内部辅助函数不要求逐个签名清单、空实现或用户审批；既有需求与授权足够明确时直接实现，只把未决产品、兼容性或权限选择交给用户。测试围绕可观察行为与风险组织，不按函数数量凑测试；文案和低风险配置修改优先使用现有校验。详见[工程改动纪律](references/engineering-discipline.md)。
4. **中大型任务在契约清单之上先写任务级 Spec**：凡跨模块、新公共 API、状态机、持久化、事件或外部集成，按 medium 起步必须 Spec；架构变化、migration、多个独立 vertical slice 属 large，另加任务依赖图。字段标准与验收线见[Spec 契约标准](references/spec-contract.md)。
5. **按假设排障**：列出 1–3 个按概率×验证成本排序的原因；为每个原因构造最小复现；确认后做最小修复并补防回归测试。连续三次失败就停止并暴露最可疑假设。难定位的 bug 或性能回归，改走 `diagnosing-bugs` 的反馈回路。
6. **Git 与隔离开发**：
   - **并行优先**：多个可独立推进的任务并存时，默认先评估并行，不默认顺着列表逐个做；选串行必须给出理由（文件重叠、阻塞边、成本）。判据与载体见 [Git 工作流与提交规范](references/git.md) §4。
   - **并行判据**：文件/缝不重叠 **且** 无阻塞边才并行；触碰同一文件、同一模块缝或互为输入的任务排串行。
   - **并行纪律**：一任务一 worktree（`../<repo>-worktree/<task-slug>/`）；同时活跃 ≤3；合并逐张收、逐张过验证门，不攒批；并行单元内部不降级——契约先行、测试、门禁照常。
   - worktree 默认建在**仓库外** `../<repo>-worktree/<directory-slug>/`；创建前检查仓库根、工作区状态、已有分支（已存在则恢复，不重建）、base branch、已有 worktrees 和目标路径；不默认删除，清理前过清理门。细节见 [Git 工作流与提交规范](references/git.md) §1；已有编排器被有意启用时由编排器拥有 worktree 生命周期。
   - 新 worktree 从已提交基准分支创建；主工作区未提交改动不会自动带入。
   - XcodeGen、Tuist 等生成型工程在新 worktree 中先生成工程再构建。
   - 分支与基准遵循当前仓库策略；没有策略时从当前任务的正确基准开描述性分支，不引入全局 Gitflow、不创建 develop、不改写历史。
   - commit / push 按用户现有授权执行，不作为每次改动的强制收尾；提交时保持单一意图，只包含本任务改动。

# 判断规则

- **显式处理冲突**：发现规则或实现模式矛盾时明确择一、说明理由，并把另一方案列为待清理，不强行折中。
- **与其他技能的配合**：

  | 技能 | 时机 | 职责 |
  | --- | --- | --- |
  | `erlin-dev-standards`（本技能） | 写的时候 | 通用工程纪律、验证、安全、Git/worktree 边界——唯一 Policy Source |
  | `erlin-autopilot` | 多任务并行编排时 | 执行流程（Inspect→切片→后端选择→合并门）；规范一律引用本技能 |
  | `erlin-arch-review` | 写完之后 | 从架构与长期维护角度审查改动 |
  | `erlin-app-coding-standards` | Swift/SwiftUI 项目 | 叠加 Swift、SwiftUI、并发、测试和 Apple 工程规范 |

- **维护约束**：
  - 每条主文档规则必须能在一个对应的 reference 中找到展开说明；reference 不得与主文档冲突。
  - 新增规则先决定归属主题：主文档只保留触发条件、不可省略的硬约束和索引；步骤、理由、例外、命令示例写入 reference。
  - 修改规则时同步更新对应 reference，并检查链接和术语；不要维护两份互相独立的完整正文。

# 输出格式

- 按需输出公共或跨模块契约（出入参、错误、边界、并发隔离）；内部签名无需逐项审批。
- 任务级 Spec：字段标准与验收线见[Spec 契约标准](references/spec-contract.md)。
- worktree 路径：仓库外 `../<repo>-worktree/<directory-slug>/`。
- 提交标题默认 `<type>: <中文描述>`；提交前检查 `git diff`、`git diff --cached` 和 `git status`，确保只提交当前任务。

# 示例

## 用户问题

“加个导出功能”“这样改行吗？要不要抽象一下？”——实现、实现决策与完成声明都在本技能管辖内。

## 工具返回

### codegraph（语义索引）

按符号查到目标导出接口与直接调用方，为复用盘点提供项目内公共资产证据。

### 测试与验证命令

只有实际执行且退出码为 0 的命令才能记为“已验证”；失败时如实上报输出原文与退出码。

## 最终输出

报告必要改动、实际验证和剩余限制；若用户授权提交，再按单一意图提交。

# 门禁

- **证据闭环**：只有实际执行且退出码为 0 的命令，才能称为“已验证/已通过”。跳过步骤、未运行的检查和失败结果必须明确报告原文与退出码。
- **失败不静默**：禁止空 `catch`、默认值吞错或把错误降级后继续。捕获错误必须处理、包装后重抛，或记录并终止，并说明可恢复性。
- **测试业务后果**：断言用户可感知或业务上的结果，不只断言函数被调用、返回非空或字段存在；每个测试独立初始化依赖，避免共享状态和执行顺序。
- **按风险验证**：行为变化、bug 修复和高风险边界补必要的测试；纯文案、低风险配置或已被现有测试覆盖的修改不强制新增测试。运行与改动相关的现有检查，如实区分通过、失败和未运行；失败或受阻可交付现状，但不得声称验证通过。
- **设置检查点**：改完文件、跑完验证或连续 5 次工具调用后，说明完成了什么、验证到什么程度、还剩什么。
- **安全底线**：
  - 不把 secret、token、密钥、私钥、生产连接串或个人信息写入代码、测试、日志、提交信息或报告；不在终端回显环境变量值。
  - 删除、覆盖、迁移、修改依赖锁文件、签名配置或数据库定义前，先检查目标并采用可回滚方案；目标与描述不符时先报告矛盾。
  - 自治边界：哪些动作可自动执行、哪些须明确授权，以《安全与失败处理规范》§4 清单为准；worktree/隔离环境不是授权边界。
- **破坏性操作**：`reset --hard`、`push --force`、已推送分支 rebase 等必须明确书面授权；未经授权不 commit、push、建 PR 或改写共享历史。
