## What it does

写代码时的通用工程规范（任何语言任何项目）——改动前先读、最小切口、证据闭环、失败不静默。动手写或改代码前、准备声称“完成/修好”前、跑测试或构建时、定位报错原因时、判断“这算不算通过”时、要开 worktree 隔离改动时、安排多任务/多票推进时使用——即使没提 skill 名。

## When to reach for it

作为叠加纪律使用——任务命中专项技能（动效/截图/课程/图标等）时由专项技能任主技能，本技能同时加载。写、改代码与推进任务的全程使用：被要求“实现/加个功能/修个 bug/重构”、写完准备声称完成、跑测试或构建、定位报错原因、判断“这算不算通过”、开 worktree 或并行隔离改动、安排多任务/多票推进或决定串行还是并行，以及拿捏“这样改行吗”“要不要抽象一下”这类实现决策时使用。与 erlin-arch-review（事后审架构）互补：本技能管写的时候，那个管写完之后。Swift/SwiftUI 项目额外叠加 erlin-app-coding-standards。

## Common questions

- **它和 erlin-app-coding-standards 什么关系？**

  后者是 Swift/SwiftUI 平台专项，叠加在它之上；通用纪律只读它一份，平台约束额外读那一份。

- **小改动也要走全套吗？**

  按风险取用：一行文案修复不需要 worktree 与 BDD，但"改前先读、改完验证"两条永远适用。

- **"证据闭环"是什么意思？**

  声称完成必须附实际验证（测试输出/构建日志/复现步骤），"应该没问题"不算证据。

## It's working if

- 每次完成声明都附实际验证证据（测试输出/构建日志/复现步骤），"应该没问题"不出现。
- diff 只含必要改动：没坏的代码没被顺手重构，无关文件零触碰。
- 跳过的步骤和失败的检查被如实报告为失败，不会被包装成"通过"。
